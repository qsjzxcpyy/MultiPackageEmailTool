## 初步业务流

业务至少包含：审单、SKU/云仓 SKU 映射、圈货与库存检查、价格一致性、历史已发记录、站内信/买家历史订单检查、数量异常、冻结与解冻、代发、虚发、多包裹物流、物流邮件、推单前地址检查、推单与云仓改 SKU、取消订单、售后表记录。

## 初步可自动化分层

### 适合先做的确定性读取/校验

- 从订单和表格提取订单号、店铺、SKU、数量、地址字段、订单状态。
- 校验必填字段、电话格式、地址长度、数量异常、重复订单。
- 根据明确的 SKU 映射表查询云仓 SKU。
- 根据明确阈值/规则标记“无异常/需人工复核”。
- 生成待确认邮件草稿、邮件变量和审计记录。

### 需要人工确认的业务决策

- 圈货不足时是等圈货、改价、单发还是代发。
- SKU 不一致或无库存时的替代策略。
- 买家历史订单/站内信是否构成风险。
- 取消、冻结、解冻、虚发、推单、改地址、改 SKU 等有副作用的操作。
- 多包裹是否只回传一个单号，及向客户发送什么内容。

## 关键风险

- 同一业务词可能对应多个系统状态，不能只靠页面颜色或自然语言判断。
- SKU、Old SKU、厂商 SKU、云仓 SKU 的映射可能随时间变化，必须版本化并保留生效时间。
- “同厂商产品”“组合商品拆分”“多个相同产品”“代发”属于组合规则，不能直接用模糊匹配自动放行。
- 订单操作不可只靠 UI 自动点击确认成功，必须执行前后读取状态并校验订单号、SKU、数量、收件信息。
- 邮件也会产生业务影响，收件人、语言、模板版本、订单号和数量必须在发送前逐项确认。

## 第一阶段推荐边界

推荐做成一个统一应用中的独立模块：`订单风险审查 -> 生成确认邮件草稿 -> 人工核对 -> 发送/记录`。第一期只读取订单导出和 SKU 映射，识别“数量明显异常”的订单并生成草稿；不自动冻结、不改库存、不推单、不取消、不改地址或 SKU。

推荐以本地应用/内部 Web 应用作为主系统，插件只作为浏览器页面取数或打开对应订单的辅助工具。可用 API 或标准导出时优先使用 API/文件；只有没有接口时才考虑浏览器自动化，且动作执行后必须重新读取状态核验。

## 目标工作流初版设计

输入：云仓发货导出文件 + 对应的原始订单文件 + 历史发送记录。

处理：读取并保存文件哈希，按订单号聚合，去除空值和重复物流号，校验物流商/订单状态/物流状态，使用原始订单文件确认订单存在，再生成唯一邮件正文。

输出：待人工确认的邮件任务；每条任务包含订单号、物流商、物流号列表、源文件哈希、正文哈希和 `PENDING_APPROVAL` 状态。未匹配、冲突、缺失或状态不支持时输出 `MANUAL_REVIEW`，禁止发送。

首个样本的预期结果：如果只使用 `ShipmentManagement.xlsx`，可生成 1 封包含 3 个 Fedex 物流号的草稿；如果同时强制要求根目录原始文件匹配，则该订单当前应被阻断为 `MANUAL_REVIEW`，因为原始文件中不存在该订单。
